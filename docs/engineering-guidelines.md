# 工程设计指南

[文档索引](README.md) · [开发流程与测试](development.md) · [当前架构与契约](architecture.md)

每次开发都必须阅读本指南。它适用于全项目的模块实现、数据维护和架构决策，包括内部运算、外部来源、界面、缓存、持久状态与执行接口。目标是让有依据的下一次变化尽量落在合适的边界内，并让尚不支持的变化得到准确处理。具体执行权限、成功证明和 Git 流程仍以对应契约为准。

前向兼容性是对未来输入和依赖变化的适度准备；同时考虑旧数据、旧调用者能否继续使用，以及升级失败后的回滚。不能承诺支持所有未知版本。简单函数、显式小表、有限适配器和清晰的不支持范围都可以是合理设计。

## 每个模块都要回答的问题

实现前检查以下问题，并让结论影响接口、数据归属和验证。现有模块只分析本次涉及的变化及其调用链，不借机改造全仓库。

1. **哪些是稳定契约，哪些只是当前样本？** 标出模块依赖的身份、字段含义、枚举、数量上限、路径、覆盖顺序、时间窗口、UI 流程与版本假设。内部受控 schema 可以严格；当前一张截图或一个上游文件不足以构成通用契约。
2. **变化是否可信？** 区分已经发生、上游已宣布、由已知机制合理推测的变化。查看相关官方文档、版本或提交历史、已有事故与样本；说明观察窗口和局限。没有证据就写未知，不能杜撰频率或把猜想当需求。
3. **变化会在哪里引发修改？** 明确可变事实的维护者、来源与适配边界；说明新增数据、版本或行为时需要改哪些地方。若同一外部事实散落多个调用者，优先收敛责任，避免同步遗漏。
4. **哪些未来输入可接受，哪些需要停止或降级？** 区分无关附加字段、显示未知值、尚未理解的业务语义、执行授权和证明条件。默认值不能把未知变成“已满足”，也不能把一个不相关的新字段扩大成整个系统不可用。
5. **投入多少才合理，如何验证？** 结合变化依据、使用频度、影响范围、发现难度与修复代价，选择最小有效方案。说明仍不支持的情况和重新评估的触发点。

低影响改动可用一句话说明没有新增易变边界或沿用哪个现有契约。新增模块或改变外部、持久边界时，应在 PR 中留下足以审查的短说明；只有重要的长期决策才同步写入相应架构专题。必读不等于每次都重新在线调研、写独立设计文档或召集审查团队。

## 用变化证据决定投入

更新次数、数据增删、语义改变、schema 破坏、UI 改版和实际故障应分开统计。发版周期只说明接触变化的机会，不直接给出破坏概率。内部功能提交不等于上游接口破坏；测试样本数也不等于实机覆盖的活动数。

调研时先确认仓库、分支、文件和消费者是否选对，再锁定 revision/tag、观察窗口与计数口径。日志分页或浅克隆不足时说明覆盖限制；不能用错误数据层的零次修改证明稳定。需要跟踪当前上游时发现其默认分支；需要复核精确实现时使用固定 commit/tag。历史结论可复用，边界、上游契约或观测变化时再更新。

| 场景 | 合理的默认投入 | 何时增加投入 |
|---|---|---|
| 稳定的内部运算、低影响局部模块 | 简单接口、明确输入语义、相关边界验证 | 实际出现第二种语义或多个调用者开始复制变化逻辑 |
| 高频更新的外部数据和接口 | 单一归一化边界、来源/版本身份、代表性历史样本及新增输入验证 | 数据刷新仍反复要求改业务代码，或变动开始改变语义 |
| 多种已观察流程或 UI 布局 | 共享身份与验收，小型按实例选择的适配器 | 新的真实布局证明既有参数化方式不足 |
| 低频但破坏后果高的持久状态、授权与证明 | 显式版本、旧语义读取/迁移/拒绝策略、身份及失败验证 | 上游或业务语义发生变化；不能因低频省略必要校验 |
| 证据不足的外部依赖 | 可替换的窄边界、明确 unknown、可定位诊断与回滚办法 | 有新契约、真实变化或重复维护成本支持进一步抽象 |

不要求精确计算 ROI 或虚构工时。说明下一次可信变化预计落在哪一层、影响什么、为何当前方案足够即可。固定列表如果小、责任明确且确需人工审核，可以继续维护；不要为不存在的第二种需求预建插件框架、注册系统或 DSL。

## 数据维护与软件边界

### 可变事实有一个维护责任

外部身份、材料配方、资源覆盖顺序、活动窗口等事实由指定来源或适配模块维护，业务调用者消费稳定含义。配置与受审查小表也可以是来源，但要说明更新责任和支持范围。展示名称、数组位置和编号前缀通常不能替代完整身份。

区分原始来源、归一化领域数据、派生缓存和执行证据。必要时保留来源 revision、获取时间、原始未知值和转换版本；不要让各下游各自猜字段含义、重复维护上限或混用不同快照。具有层叠覆盖语义的来源必须与实际消费者一致，不能按修改时间选文件或无依据地合并所有表。多消费者应复用同一解析责任；必须独立实现时，用一致性验证防止漂移。

### 把变化限制在有含义的边界

来源 adapter 负责外部协议变化，领域模块负责稳定业务含义，执行层负责授权和效果证明。展示的新状态可以显示“未知”；新的必需选人约束不能默认满足；新增 SDK 中间事件不能成为成功事件。能力发现与执行许可分开，新客户端、难度、道具被识别不意味着允许使用。

外部协议按需要投影字段，允许语义无关的扩充，保留有意义的未知值。不要仅因字段陌生就认定它无关，尤其新增约束、状态和单位。授权、身份、约束及成功条件仍严格校验。未知业务语义应限制受影响能力并给出原因；明确授权的有限研究可以继续，但不能把未建模机制、静态校验或人工确认冒充执行成功。

共享稳定流程，只对有观察依据的变化轴参数化。数据目录与 UI 路径应分工：目录决定身份、版次和开放窗口，适配器决定已观察的交互，独立验收确认实际到达的精确目标。未知版式应保留诊断及有限研究入口，避免每个新活动复制整套流程，也避免宣称同一组坐标可以支持所有未来活动。

### 缓存和持久状态采用不同兼容策略

- **可重建缓存**：复用必须绑定决定语义的来源、请求参数和身份，可以放在 key 或可校验的 metadata 中；派生缓存另绑定转换版本，不兼容时失效重建。原始不可变来源不需要因 parser 更新复制存储。字节 hash 只证明字节一致，不能替代 freshness、业务语义或授权窗口。缓存和在线结果经过相同的语义校验。只读展示可以保留明确标记时间与限制的旧数据，不能将它重新当作当前执行授权或证明。
- **用户维护数据和持久业务状态**：明确读哪些旧版本、写哪个版本，以及迁移、备份、幂等和回滚条件。旧字段缺失不能用默认值制造新权限；未来未知版本不能按当前版本强行解释。
- **历史证据和追加审计**：保持原字节及身份不变。新的读取 adapter 或派生视图可以兼容展示；不得为了升级重写旧 receipt、补造证明或替换失败终态。

兼容桥和临时特殊处理应有支持范围与退出条件，例如下一次完整更新生成新格式、停止支持某个已退出的版本。不要无限保留无法验证的旧路径，也不要把清理的所属范围扩大到未来未知文件。

## 验证下一次可信变化

对本次边界选择能改变结论的少量场景：当前正常输入、一个相关历史输入，以及一个有依据的未来变化或对抗性反例。没有历史输入时说明缺口，不制造“历史 fixture”。按影响选择测试、离线回放或代码/链接核对；纯文档和低影响改动不需要新增镜像实现的测试。

可选反例包括：新增可选字段仍可读，新增未知必需约束不能满足，资源上层覆盖下层而非并集，同编号不同活动版次不共用特殊导航，过期缓存不能延长授权，新状态不能伪造成功，旧持久语义不能迁移出更大权限。断言应验证行为、身份与失败原因，不能只匹配代码字串或证明“没有抛异常”。只测 hash 或 loader 成功不能证明最终消费者使用了正确内容。

重要新边界或反复出现的泛化失败，应独立审查或做一次 forward-test：让审查者仅依据指南处理一个真实的新模块/变更请求，检查其设计选择和验证是否合理，再修改误导性指令。独立审查不代替测试，也不要求每次开发使用 subagent、真实模型或设备。真实执行仍遵循[测试策略](development.md#测试策略)及对应授权。

PR 可用短段落说明：**变化依据 → 可信的下一次变化 → 边界与投入选择 → 验证和限制 → 重新评估条件**。这是审查信息，不是额外审批流程。

## 历史校准样例：资源与导航

以下为研究观察，用于说明如何做判断，不是未来周期承诺，也不把本指南限定为 MAA。窗口为 **2026-07-12 00:00 UTC（含）至 2026-10-10 00:00 UTC（不含）**，90 天；日期按 UTC 去重。

| 观察对象 | 路径修改/发布数 | 更新日数 | 语义复核或限制 |
|---|---:|---:|---|
| MaaResource Tile `overview.json` | 11 | 9 | 10 次仅新增身份，0 次删除或修改已有身份值；另 1 次解析后无变化 |
| MaaResource `stages.json` | 9 | 8 | 4 次含新增身份，5 次含删除身份；它不是完整关卡目录 |
| MaaResource `battle_data.json` | 26 | 19 | 7 次含新增身份，25 次含已有值变化；分类可重叠，不能据此判定破坏 |
| Core `resource/tasks/tasks.json` | 64 | 34 | 源码路径修改，不等于 UI 改版数；MaaResource 不含此文件 |
| Core stable release | 19 | 16 | 4 次 minor 首发、15 次 patch，呈簇状；发布间隔不固定 |

资源统计固定在 [MaaResource b477a923](https://github.com/MaaAssistantArknights/MaaResource/tree/b477a923dcb73be1d604189dedbcdb4802627f63)，来自完整 Git 历史；Core tasks 固定在 [0fdb0e39](https://github.com/MaaAssistantArknights/MaaAssistantArknights/tree/0fdb0e394f92792994d89bdf65867dfc1acf21c8)，经官方 commits API 完整分页；发布来自[官方 releases](https://github.com/MaaAssistantArknights/MaaAssistantArknights/releases)。统计是本项目的推导，方法为按 committer 时间过滤路径提交、按 published_at 过滤非 draft/非 prerelease 发布，再对资源各提交与第一父提交的 JSON 按身份比较。新增/删除/已有值改变和容器类型改变分别计数；格式变化仍可能算路径提交。调查通过[仓库元数据](https://api.github.com/repos/MaaAssistantArknights/MaaAssistantArknights)发现默认分支当时为 `dev-v2`，硬编码 `dev` 已返回 404；这只证明该假设可失效，不能推测改名频率。

在这个窗口中，资源比 stable bundle 更早包含新活动地图，Tile 地图身份的变化主要表现为新增内容；其它表同时存在删除或已有值改变。因此应投入正确的生效层读取、同代身份和覆盖验证，让新增关卡不依赖逐关改代码；不能从更新频率推出放弃整代兼容验证或总取任意 latest。

跨活动导航的现有依据见[导航样本说明](../tests/fixtures/navigation/README.md)和[测试策略](development.md#测试策略)。主线、资源关、归档与当前活动已有不同识别路径，DV 与 NL 有按版次/分区限定的特殊适配。元数据 route、脱敏协议 fixture、OCR 画布与完整实机验收的覆盖不同；现有材料不足以估计未来 UI 改版频率，但足以支持分离身份目录、公共执行验收和有限布局适配。

其它模块也已有演化依据：Box/森空岛数据扩展、SDK adapter 迁移、能力账本旧语义迁移和 receipt 兼容桥，见[架构](architecture.md)、[恢复](recovery.md)及[历史记录](history.md)。这些能证明变化轴存在，不能当作外部 breaking 频率。对应模块要按其自身证据和后果作决定，不能直接套用地图表的更新周期。
